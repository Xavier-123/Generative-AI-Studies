## A. 分布式优化

| 并行方式 | 核心思想                                |
| -------- | --------------------------------------- |
| **DP**   | 复制模型，多 GPU 分不同数据             |
| **TP**   | 一个层内部切矩阵                        |
| **PP**   | 不同 GPU 放不同层                       |
| **EP**   | MoE 专家切分                            |
| **SP**   | 切 sequence，降低激活显存               |
| **CP**   | 切 context，降低长上下文 Attention 开销 |



| 类型   | 全称              | 中文       | 解决的问题                | 切分维度             | 主要切什么    | 典型场景         |
| ------ | ----------------- | ---------- | ------------------------- | -------------------- | ------------- | ---------------- |
| **DP** | Data Parallel     | 数据并行   | 数据太多，提升吞吐        | Batch 维度           | 数据          | 所有模型训练     |
| **TP** | Tensor Parallel   | 张量并行   | 单层参数/计算太大         | Hidden/Matrix维度    | 权重矩阵      | 大模型单层计算   |
| **PP** | Pipeline Parallel | 流水线并行 | 模型层数太多放不下        | Layer维度            | Transformer层 | 超大模型         |
| **EP** | Expert Parallel   | 专家并行   | MoE专家数量太多           | Expert维度           | Expert网络    | DeepSeek/Mixtral |
| **SP** | Sequence Parallel | 序列并行   | 长序列激活显存大          | Sequence维度         | Activation    | Megatron训练     |
| **CP** | Context Parallel  | 上下文并行 | 超长Context Attention爆炸 | Sequence/Context维度 | KV/Attention  | 128K+上下文      |



**核心目标**：通信层面优化，解决单卡显存装不下超大模型、或单卡算子吞吐达不到要求的分布式并行问题。

#### 张量并行 

核心问题：

> **单个 Transformer Layer 太大，一张 GPU 放不下，或者计算太慢。**

Tensor Parallelism（TP）。如 Megatron-LM TP，将 Linear 层的权重矩阵按行或列切分到多卡，降低单卡显存并并行计算，但通信频率较高（需要 All-Reduce/All-Gather）。



#### **流水线并行**

Pipeline Parallelism(PP)。将模型的 Transformer 层按层切分部署在不同 GPU 上，以 Stage 方式串行/流水化处理，适合跨节点/大模型部署。

核心问题：

> **整个模型层数太多，单卡根本放不下。**

#### 序列并行 / 上下文并行 (Sequence / Context Parallelism, SP/CP)

针对超长上下文场景（如 128k+），将 Sequence 维度切分到多卡并行处理（如 DeepSpeed-Ulysses、Ring-Attention）。



#### 专家并行 (Expert Parallelism, EP)

针对 MoE（混合专家模型），将不同的 Expert 分散部署在不同 GPU 上，利用 All-to-All 算子进行 Token 路由通信。



#### 计算与通信重叠 (Communication-Computation Overlap)

在 TP/EP 中利用 Async NCCL 通信，将 GEMM 计算与跨卡通信（All-Reduce/All-to-All）在时间线（Stream）上重叠，隐藏通信开销。

## B. 低比特量化

**核心目标**：降低权重与激活值的数值精度，从而减少显存占用并提升计算/访存效率。

```json
输入文本
  ↓
词嵌入层 (Embedding) ← 适合量化
  ↓
循环N次 Transformer块:
  ├── LayerNorm ← 不适合量化
  ├── 自注意力层
  │   ├── QKV投影(线性层) ← 非常适合量化  
  │   ├── 注意力计算 ← 部分适合
  │   └── 输出投影(线性层) ← 非常适合量化
  ├── LayerNorm ← 不适合量化
  └── 前馈网络
      ├── 线性层1 ← 非常适合量化
      ├── GELU激活 ← 不太适合量化
      └── 线性层2 ← 非常适合量化
  ↓
LayerNorm ← 不适合量化
  ↓
输出层(线性层) ← 较敏感，谨慎量化
  ↓
最终输出
```



#### Weight-Only 量化 (如 INT4/INT8/FP4)

仅对权重矩阵量化，激活值维持 FP16/BF16，适合 Decode 阶段（访存密集型）。典型算法有 **AWQ**（保护显著通道）、**GPTQ**（二阶梯度补偿）、**SqueezeLLM**。





#### Weight-Activation (W&A) 联合量化

权重和激活值同时量化（如 INT8 W8A8、FP8 W8A8），使计算能够真正走硬件低精度 INT8/FP8 Tensor Core，大幅提升算力上限。典型算法有 **SmoothQuant**、**OmniQuant**。



#### FP8 原生精度推理

利用现代 GPU（如 Nvidia H100/H200/B200）硬件支持的 FP8（E4M3 / E5M2）格式进行高吞吐推理。

| 量化方式                | 量化对象                  | 核心目标            | 离线处理过程（具体实现）                       | 模型保存内容                        | 推理计算过程                              | 代表方法                                |
| ----------------------- | ------------------------- | ------------------- | ---------------------------------------------- | ----------------------------------- | ----------------------------------------- | --------------------------------------- |
| **FP16/BF16 原始推理**  | 无量化                    | 保证精度            | 不处理                                         | FP16 Weight                         | FP16 × FP16 → FP16/BF16                   | 原始模型                                |
| **Weight-Only INT8**    | 仅 Weight                 | 降低显存            | FP16权重 → INT8权重 + scale                    | `W_int8 + scale(fp16)`              | INT8 weight → kernel反量化 → FP16 GEMM    | LLM.int8部分场景                        |
| **Weight-Only INT4**    | 仅 Weight                 | 极限压缩显存        | FP16权重 → INT4权重 + group scale + zero point | `W_int4 + scale + zero`             | INT4 weight读取 → 在线dequant → FP16 GEMM | GPTQ、AWQ                               |
| **Weight-Only FP8**     | 仅 Weight                 | 降低显存+保持精度   | FP16 Weight → FP8 Weight                       | `W_fp8 + scale`                     | FP8 weight → FP16/FP8计算                 | FP8 checkpoint                          |
| **W8A8 INT8**           | Weight + Activation       | 提升计算吞吐        | W量化 + 校准Activation范围                     | `W_int8 + X_scale + W_scale`        | INT8 × INT8 → INT32累加 → FP16输出        | SmoothQuant                             |
| **W4A8**                | Weight + Activation       | 极限压缩+高速       | Weight INT4，Activation INT8                   | INT4 weight + INT8 activation scale | INT4/INT8混合kernel计算                   | 部分研究方案                            |
| **FP8 Mixed Precision** | Weight + Activation       | 利用Tensor Core加速 | FP16/BF16 → FP8                                | FP8 weight + scaling factor         | FP8 Tensor Core计算，FP16累加             | NVIDIA Transformer Engine、DeepSeek FP8 |
| **混合精度Outlier量化** | 大部分Weight + 少量异常值 | 保精度              | 普通值INT8，异常值FP16                         | INT8 weight + FP16 outlier          | INT8 GEMM + FP16补偿                      | LLM.int8()                              |



#### KV Cache 量化

将历史存储的 Key/Value 矩阵量化为 INT8/INT4/FP8 格式，显著降低长文本与高并发下的显存开销。

KV Cache 量化就是把历史 token 的 K/V 张量从 FP16 压缩成 FP8/INT8/INT4，并保存必要的 **scale**；生成新 token 时，在 Attention kernel 内融合反量化，使低精度 KV Cache 参与高精度 Attention，从而减少显存占用，提高长上下文吞吐。

计算 scale：
$$
scale=max(|x|)/127
$$
量化：
$$
q=round(x/scale)
$$

## C. 算子优化

**核心目标**：从底层（CUDA/Triton 级）榨干 GPU 硬件的计算与访存潜能，减少 Kernel Launch 开销与访存瓶颈。



### FlashAttention 系列 (v1/v2/v3)

通过 IO 感知与 Tiling（分块）技术，将注意力计算限制在 GPU SRAM 内，极大减少了对 HBM（显存）的频繁读写。

FlashAttention 本质上不是改变 Attention 数学公式，而是**重新设计 Attention 的 GPU 计算方式**，通过减少 GPU 显存（HBM）和片上高速缓存（SRAM）之间的数据搬运，提高吞吐。它的核心思想是 **IO-Aware Attention（感知内存访问的 Attention）**。

理解 FlashAttention，重点抓住三个关键词：

1. **Tiling（分块计算）**
2. **Online Softmax（在线 Softmax）**
3. **Kernel Fusion（算子融合）**





### FlashDecoding / FlashDecoding++

针对 Decode 阶段（SeqLen=1）优化 Attention，通过在 KV 序列维度上引入并行度，解决 Decode 阶段 GPU 算力利用率低的问题。

核心思想：将长KV Cache切分成多个块，让多个GPU线程块并行处理，然后通过Online Softmax合并结果。

|          | FlashAttention          | FlashDecoding             |
| -------- | ----------------------- | ------------------------- |
| 主要阶段 | Prefill                 | Decode                    |
| Q长度    | N                       | 1                         |
| K/V长度  | N                       | N                         |
| 瓶颈     | HBM访问                 | KV Cache读取              |
| 优化目标 | 减少Attention Matrix IO | 提高并行度                |
| 核心技术 | Tile + Online Softmax   | KV Split + Online Softmax |
| 适合     | 训练、长Prompt          | 生成阶段                  |

**FlashAttention → Prefill加速**

**FlashDecoding → Decode加速**

**PagedAttention → KV Cache管理**

**Continuous Batching → 请求调度**



### 算子融合 (Kernel Fusion)

将多个连续的小算子（如 RMSNorm、RoPE 位置编码、SwiGLU 激活函数、Element-wise 操作）手写/编译融合为一个大 Kernel，减少 HBM 访存和内核启动开销。

Kernel Fusion底层实现原理

Kernel Fusion 是通过将多个连续 GPU 算子合并为一个 CUDA Kernel，减少 Kernel launch 开销以及 GPU Global Memory 的读写次数。实现方式通常包括手写 CUDA/Triton Kernel、编译器自动融合（如 TorchInductor）。融合后的 Kernel 将中间计算结果保存在 GPU register 或 shared memory 中，避免中间 Tensor 写回 HBM。例如 RMSNorm+Add Fusion 中，传统方式需要 Add Kernel 写回结果，再由 RMSNorm Kernel读取；融合后一次读取输入，在寄存器中完成残差计算、归一化和缩放，最后只写一次输出，从而显著降低显存带宽压力。

## D. 服务并发优化

**核心目标**：提升 serving 系统的并发能力、整体吞吐量（Throughput）与服务 SLA（如 TTFT 首字延迟、TFT 逐字延迟）。



#### 连续批处理 (Continuous Batching / In-flight Batching)

打破传统 Static Batching 的限制，在 Token 级别动态调度请求。一旦某个请求生成结束立即退出，新请求立即插入 Batch，极大消除了 Padding 浪费。



#### Prefill 与 Decode 解耦/分离 (PD Separation)

将计算密集型的 Prefill 阶段（高算力要求）与访存密集型的 Decode 阶段（高带宽要求）部署在不同的物理集群/节点上，避免互相抢占资源（如 Mooncake、Splitwise、DistServe）。

传统prefill在batch输入的时候，是先将不同长度的seq都计算完了之后，再统一decode生成token。

**传统 Prefill + Decode 流程**：

Step 1：统一 Prefill（GPU Tensor Core 利用率高；FLOPS 使用率高；计算压力大）；

Step 2：Prefill全部完成后进入Decode（GPU算力闲置；显存带宽成为瓶颈）；

问题：最长 Prompt 会拖慢所有请求。

**PD分离最关键的问题：KV Cache怎么传？**

方法1：GPU Direct KV Transfer

方法2：KV Cache Store

| 方式                     | 流程                                 | 是否等待最长seq |
| ------------------------ | ------------------------------------ | --------------- |
| 传统Batch推理            | Prefill整个batch → Decode            | 是              |
| Bucket Batch             | 相近长度组成batch → Prefill → Decode | 减少            |
| vLLM Continuous Batching | 动态Prefill/Decode混合               | 基本避免        |



#### Chunked Prefill (分块 Prefill)

将超长 Prompt 拆分为小块（Chunk），与 Decode 阶段的 Token 混合在一个 Batch 中计算，平滑系统的 P99 延迟，防止长请求卡死短请求。



#### 动态 Batch & 资源感知调度

根据实时显存剩余量、请求长度以及 KV Cache 动态开销，自适应调整 Batch 大小及请求优先级。

## E. 显存优化

**核心目标**：消除显存碎片、降低 KV Cache 的空间占用，让单卡能装下更长上下文和更多并发。



#### PagedAttention

借鉴操作系统虚拟内存的分页机制，将 KV Cache 切分为固定大小的 Block 离散存储在显存中，消除了外部显存碎片，使显存利用率提升至接近 100%（vLLM 核心技术）。

| 技术                | 解决问题                  | 阶段      |
| ------------------- | ------------------------- | --------- |
| FlashAttention      | 减少Attention计算显存访问 | 训练/推理 |
| PagedAttention      | 优化KV Cache存储          | 推理      |
| Continuous batching | 提高请求吞吐              | 推理      |



#### 注意力架构演进 (MQA / GQA)：

- **MQA (Multi-Query Attention)**：所有 Query 头共享一组 Key/Value 头。
- **GQA (Grouped-Query Attention)**：Query 头按组共享 Key/Value 头（如 Llama 2/3）。相比传统的 MHA，KV Cache 显存占用可降低 4x~8x。
- **MLA（Multi-head Latent Attention）**：降低 KV Cache 的显存占用，同时尽量保持 Multi-Head Attention 的表达能力。把 KV 压缩到一个低维潜在空间（Latent Space），存储压缩后的 latent cache。

```
MHA:

Q1 ---> K1,V1
Q2 ---> K2,V2
Q3 ---> K3,V3
...
Q32 --> K32,V32


MQA:

Q1 ---\
Q2 ----\
Q3 ----- > K,V
...
Q32---/
```



| 机制 | KV Cache存储  | 压缩方式 | 表达能力 |
| ---- | ------------- | -------- | -------- |
| MHA  | 完整KV        | 无       | 最高     |
| MQA  | 1组KV         | 减少head | 下降明显 |
| GQA  | 少量KV head   | 分组共享 | 中等     |
| MLA  | latent vector | 低秩压缩 | 较高     |



| 技术          | 压缩方式        | 是否需要scale |
| ------------- | --------------- | ------------- |
| MQA           | 减少KV Head     | ❌ 不需要      |
| GQA           | 减少KV Head     | ❌ 不需要      |
| MLA           | 学习latent压缩  | ❌ 不需要      |
| INT8 KV Cache | 数值量化        | ✅需要         |
| FP8 KV Cache  | 数值量化        | ✅通常需要     |
| MLA + FP8     | latent压缩+量化 | ✅需要         |





#### KV Cache 剪枝与压缩 (KV Cache Pruning/Eviction)

通过算法丢弃不重要的 KV Token（如 **StreamingLLM** 保留 Attention Sink 和滑动窗口；**H2O** 保留 Heavy Hitter Token）。



#### 前缀缓存 (Prefix / Prompt Caching)

对系统 Prompt、常用模板或多轮对话的前缀 KV Cache 进行复用与 Hash 缓存，避免重复 Prefill 计算并节省显存。

**请求来了如何命中缓存？**

将prompt拆为多个block，计算每个block的哈希值，然后去prefill cache匹配

**KV Cache如何共享？**

引用计数（Reference Count）

**Prefix Cache如何淘汰？**

最久未使用以及引用次数为0

|          | 普通KV Cache       | Prefix Cache                  |
| -------- | ------------------ | ----------------------------- |
| 生命周期 | 单个请求           | 多个请求共享                  |
| 目的     | 避免decode重复计算 | 避免prefill重复计算           |
| 作用阶段 | Decode             | Prefill                       |
| 共享范围 | 一个request        | 多个request                   |
| 释放方式 | 请求结束释放       | 引用计数/LRU                  |
| 典型场景 | 聊天生成           | 系统Prompt、多轮历史、RAG模板 |



#### 显存/内存/NVMe 卸载 (Offloading)

在超长上下文或显存极度紧缺时，将暂时用不到的 KV Cache 或模型权重动态 Offload 到 CPU 内存或 NVMe SSD 中。

## F. 其它优化技术

**核心目标**：不属于上述单一范畴、或跨领域的算法创新与架构替代方案。
**典型技术**：

- **投机采样 (Speculative Decoding)**：使用一个小而快的 Draft Model（草稿模型）并行生成多个 Token，再由大模型（Target Model）一次性并行验证。变相将逐字 Decode 转为类似 Prefill 的并行验证，大幅提升单请求生成速度（如 Medusa、EAGLE-1/2）。
- **模型剪枝与蒸馏 (Pruning & Distillation)**：
  - **结构化剪枝**：直接剪裁掉不重要的 Layer、Head 或 Channel，降低模型参数量。
  - **知识蒸馏**：将大模型（如 70B/405B）的推理能力蒸馏至小模型（如 8B/3B），保持较高精度的同时提升推理效率。
- **线性注意力与非 Transformer 架构替代 (SSM / Linear RNN)**：
  - 采用 **Mamba (SSM)**、**RWKV**、**RetNet** 等具备复杂度的新架构。这类架构在 Decode 阶段只需要固定大小的 State 向量，从根本上消除了随着上下文增加而不断膨胀的 KV Cache 瓶颈。
