这个多 Agent 协同结构的设计非常巧妙，它本质上是用**“分治法（Divide and Conquer）”**和**“编译期/运行期分离（动静隔离）”**的思想，解决了大模型在处理复杂多分类（特别是有交集、易混淆类别）时**Prompt 过长、注意力分散、边界模糊**的痛点。



“主分类 + 易错诊断 + 专有二分类”思想：构建金标数据集（尽量覆盖当前阶段的真实场景），然后先用主分类跑一遍数据，可以总体判断哪些类别准确率和召回率高，标为“易分类别”，然后再重新进入自进化agent系统优化，第一步进入主分类，去经验库中获取topk的分类经验动态组装提示词，如果分为“易分类别”，则该条数据的流程结束，并且使用非参数GRPO算法从多个类别提取分类经验；第二步，统计分析所有判定为其它类别的数据，看看哪些类别容易混淆（比如类别A有很大比例的数据都误判为B，则认为A，B两类别容易混淆），制作新的两类数据集；第三步，将所有两类数据集，传入专有二分类，通过非参数GRPO优化具有针对性的提取两个类别间的经验，并保存到经验库。

具体例子为：假设有A、B、C、D、E、F六个类别的数据，EF被认为易分类别，则经过主分类后，我们需要统计分析ABCD这四个类别数据，分析出 A、B、C 这三个类别易混淆，即A容易判断为B，A也容易判定为C，那么在设计专有二分类的时候，我们可以将B和C合为一个新的类别，A和其它，经过第一个专有二分类之后如果判定为A则结束，如果认定为其它，则再经过一次专有二分类用于学习判定B和C的边界条件。

主分类提取经验可以理解为从宏观提取经验，专有二分类理解为微观提取经验

##### 模拟问题

###### Q1：为什么选择"无训练"方案而不是直接微调模型？

> **回答要点**：微调成本高（算力、数据标注）、周期长、难以快速迭代；无训练方案通过推理阶段积累经验，零算力成本、实时可更新，适合资源受限的业务场景。可对比 RAG（检索外部知识）与本方案（自生成内部经验）的差异。
>
> 原因1：场景变化太快(SFT 周期非常长)
> 原因2：数据规模不足(SFT 500~3000条标注数据)
> 原因3：解释性要求高(SFT 难解释)

###### Q2：为什么选择 TextGrad 框架？它们的核心差异是什么？

> **回答要点**：TextGrad 将"文本梯度"概念引入优化，适合需要多跳推理的复杂任务。

###### Q3：经验库如何避免"噪声经验"污染后续推理？

> **回答要点**：通过两阶段机制：① 单 Batch 内先生成 candidate_experiences 而非直接更新，避免单条坏样本直接写入；② Epoch 结束后的压缩阶段通过 LLM 二次审查合并冗余、淘汰低质量条目。可进一步讨论设置置信度阈值等改进方向。

>   。若某条经验加入后 ΔAcc < 0，说明该经验存在负迁移，应予以剔除或降级。

> 1. **留一交叉验证（Leave-One-Out Validation）**：

>    - **评估指标**：计算经验的**边际贡献度**。边际贡献为负或接近于零的经验会被标记为“低效经验”，触发清理机制。

###### Q8：新沉淀的经验与既有经验产生逻辑冲突，如何解决？（+1）

> 1. **语义冲突检测（Conflict Detection）**：
>    - **方法**：利用专有的“审计 Agent”或符号化规则，对新生成的 JSON 经验与既有经验进行两两比对。
>    - **评估案例**：若经验 A 指出“‘退款’关键词属于‘售后服务’”，而新经验 B 指出“‘退款’且伴随抱怨语时应归入‘投诉’”，系统需评估两者的覆盖边界。
>    - **解决机制**：若判定为冲突，则触发“规则融合（Merge）”或“条件细化（Refinement）”，通过补充前置条件（如 Context-specific constraints）来消解冲突。
> 2. **语义冗余度与合并（Redundancy & Deduplication）**：
>    - **方法**：计算新经验与旧经验在向量空间（Embedding）中的余弦相似度。
>    - **评估指标**：当相似度超过设定阈值（如 0.85）时，判定为表述冗余。系统将自动调用大模型进行“规则归并”，用更具泛化性的表述合并这两条经验。

###### Q9：如何提升跨样本的泛化能力？

> **回答要点**：高温度增加输出多样性，保证 N 条采样轨迹覆盖不同推理路径（正确与错误），为经验提取提供更丰富的对比素材。若 temperature 过低，N 条输出高度相似，经验提取价值有限。
>
> 1. **跨批次泛化测试**：
>    - **方法**：将在批次 T 中提炼出的经验，立即在完全独立的批次 T+1、T+2 上进行盲测。
>    - **评估指标**：**泛化衰减率。如果在提炼批次上准确率提升 15%，但在新批次上仅提升 1%，说明该经验过拟合了特定批次的语料（如特定客户的说话口癖），属于低质量经验。
> 2. **生存周期与置信度衰减**：
>    - **方法**：给每条 JSON 经验赋予一个初始置信度（Confidence Score）和调用计数器。
>    - **评估机制**：在后续标注中，每当某条经验被成功检索并调用：
>      - 若导致标注正确：置信度增加（奖励）；
>      - 若导致标注错误：置信度大幅扣减（惩罚）。
>      - 当置信度低于阈值，或者长期未被调用，该经验将被自动物理删除或归档，以保持经验库的“代谢活性”。
> 3. **引入“黄金验证集”的门禁机制**：
>    - **方法**：在每次经验库或 Prompt 更新后，不能仅依赖当前 Batch 的准确率，还需自动在代表性历史样本集上进行微调级别的回归测试。

###### Q10：`temperature=1.0` 的设计意图是什么？

> **回答要点**：高温度增加输出多样性，保证 N 条采样轨迹覆盖不同推理路径（正确与错误），为经验提取提供更丰富的对比素材。若 temperature 过低，N 条输出高度相似，经验提取价值有限。

###### Q11：这套系统如何从实验原型落地到生产环境？你会做哪些工程化改造？

###### Q18：GRPO的奖励函数如何设计的？

```markdown
第一步：考核候选提示词的“三个指标”
	答得对不对（正确率得分）
	答得清不清晰（边界区分得分），这里不需要
	是不是太啰唆（字数冗余扣分），这里不需要

第二步：同台竞技，只看“相对优势”（GRPO 核心）
	每次迭代，系统会同时生成 5∼10 个不同的提示词版本。
    让这些版本在同一批测试数据上“同台竞技”，算出各自的总分（分析轨迹 + 最终答案）。
    计算它们的平均分。
    比平均分高得多的，定义为**“尖子生（正向反馈）”；比平均分低得多的，定义为“不及格生（逆向反馈）”**。
    文本梯度系统只会参考“尖子生”和“不及格生”的答题差异来进行针对性反思。
    
第三步：自适应调整考核重点（动态风控）
	模式 A：低分低谷期（系统还很笨的时候，比如正确率低于 60%）
    	考核重点：只看正确率。只要能答对，逻辑粗糙点、提示词长一点都没关系。
    	更新门槛：降到最低。只要有稍微好一点的修改，立刻通过，鼓励系统大胆探索。
    模式 B：高分平稳期（系统已经很聪明的时候，比如正确率高于 85%）
    	考核重点：转向边界清晰度和字数精简度。正确率高已经不稀奇了，我们要看谁的推理逻辑最干净、字数最少。
    	更新门槛：提到最高。只有能带来显著突破且不啰唆的修改才允许上线，防止系统“瞎折腾”导致线上不稳定。
```



###### Q20： 动态经验库的“规则冲突”与一致性如何维护？（+1）

1. **编译期冲突检测与消解机制（Consistency Checking）**：
   - 当有新规则拟写入经验库时，审计 Agent 负责检索库中语义相似的已有规则，并利用大模型进行一致性推理。
   - 若发现冲突，进行**“规则合并（Consolidation）”**，融合成一条描述更精确、边界更清晰的上位规则，或者通过显式声明优先级（e.g., if A then X, unless B）来解决。
2. **规则的时效性衰减（Time-decay / Usage-decay）**：
   - 为每条规则维护一个使用计数和准确率反馈指标。如果某条规则长期未被检索，或者被检索后导致线上推理判断失误，则降低其置信度权重，直至触发动态剪枝。

###### Q2： **你们怎么定义“幻觉”？是怎么量化的？**

```markdown
1）事实幻觉（Factual Hallucination）
	定义为：Answer 中的关键事实与可信知识源（retrieval / dataset / knowledge base）不一致
	量化方式：
        是否有 unsupported claim（RAGAS）
        是否存在 retrieval mismatch
        是否无法在 evidence 中找到支撑
2）推理幻觉（Reasoning Hallucination）
	定义为：推理链中任意 step 逻辑不成立，但最终答案可能看似正确
	量化方式：
        step-level verification（CoVe）
        self-consistency disagreement rate
        judge model 对 reasoning chain 的打分
```

###### Q14：三级轻量索引：底层数据结构的分层设计

| 索引层级           | 存储内容                                     | 构建方式                                 | 核心作用                             |
| ------------------ | -------------------------------------------- | ---------------------------------------- | ------------------------------------ |
| 关键词级（隐式层） | 语块的原始全文文本                           | 离线不做预索引，查询时实时做精确文本匹配 | 支撑精确实体、专有名词的快速定位     |
| 句子级（语义层）   | 每个单句的稠密向量 + 句子→所属语块的映射关系 | 对每个语块分句，逐句计算嵌入向量         | 支撑细粒度语义匹配，精准定位相关句子 |
| 语块级（全文层）   | 1000token 左右的完整语块文本 + 元数据        | 按句子边界切分语料，保证语义完整         | 作为最终读取单元，提供完整上下文     |



###### Q15：三类分层检索工具

| 检索工具                    | 对应索引层级       | 工作机制                                                     | 模型使用场景                                           |
| --------------------------- | ------------------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| `keyword_search` 关键词检索 | 关键词级（隐式层） | 基于精确词法匹配，按「关键词出现次数 × 关键词长度」打分，返回包含关键词的句子片段 | 已知明确实体、专有名词、数字、日期，需要精准定位语块时 |
| `semantic_search` 语义检索  | 句子级（语义层）   | 基于句子向量做余弦相似度匹配，按语块内最高相似度句子打分，返回匹配句子片段 | 关键词检索失效、需要概念性 / 模糊语义匹配时            |
| `chunk_read` 语块读取       | 语块级（全文层）   | 根据语块 ID 返回完整文本，配合上下文追踪器避免重复读取       | 通过前两类工具筛选出高相关语块后，读取全文做深度推理   |



###### Q16：分层检索的完整工作流

三级索引是 “数据底座”，三类工具是 “访问入口”，二者一一对应，共同实现**渐进式、按需式的分层检索**，这也是和传统单轮 RAG 最核心的区别：

1. 模型先通过 `keyword_search` 或 `semantic_search` 做**粗筛**：只返回句子级片段，用极少 token 快速判断哪些语块可能相关；
2. 模型自主判断相关性后，再通过 `chunk_read` 做**精读**：只对高相关语块读取完整全文，避免大量无关内容占用上下文；
3. 若信息不足，模型可自主切换检索工具、调整关键词 / 查询，反复迭代补全证据链，直到信息足够再输出答案。

简单来说：**三级索引定义了 “有什么信息可以用”，三类工具定义了 “模型怎么用这些信息”**，二者结合实现了 “检索粒度由模型自主决定”，这就是 Agentic RAG 的核心体现。

###### Q19：阶段一：查询优化

​		对原始问题做结构化拆解：识别问题类型（单跳 / 多跳 / 开放域）、拆分多跳子问题、生成适配不同检索工具的查询表达式，输出结构化的子问题列表与对应检索 Query，为后续检索和推理明确方向。

**与自纠错闭环的联动**

- 首次执行时，按默认拆解逻辑运行，是全链路的起点；
- 接收反思阶段回退的「查询修正指令」：当后续验证发现问题理解偏差、子问题拆解错误、检索方向完全跑偏时，反思阶段会输出具体的重写要求（如 “补充时间限定条件”“将复合问题拆分为两个独立子问题”），本阶段根据指令重新改写查询，再从头走后续链路。

**输出产物**：结构化子问题列表、对应检索关键词 / 语义查询、问题约束条件



###### Q20：阶段二：自主检索

基于 A-RAG 分层检索框架执行证据收集，这是**内层的第一级自迭代循环**：大模型通过 ReAct 模式自主调用三类分层检索工具（`keyword_search`精确匹配、`semantic_search`语义匹配、`chunk_read`全文读取），自主判断信息是否充足、自主切换检索策略，直到认为证据可支撑推理，再进入下一阶段。

这个过程本身就是检索层面的自纠错 —— 模型会自主修正检索关键词、更换检索工具、补充读取语块，无需外部规则触发。

**与自纠错闭环的联动**

- 接收反思阶段回退的「检索补全指令」：当验证发现证据缺失、事实冲突、实体信息不全时，反思阶段会输出定向检索要求（如 “精确匹配 XX 实体的任职时间”“补充 XX 事件的背景上下文”）；
- 本阶段根据指令定向执行检索：优先用关键词检索锁定目标语块，读取全文补充证据，必要时读取相邻语块完善上下文，完成证据补全后直接送入推理阶段重算，无需回到查询改写阶段，最小化重复计算。

**输出产物**：带来源标注的证据语块集合（含 chunk ID、原文片段、检索方式）、已读语块追踪记录。



###### Q21：阶段三：多路径推理

基于已收集的证据集，融合 Graph of Thoughts 与 Self-Consistency 思想，生成多条独立的推理路径，每条路径完整推导答案并标注证据支撑点，最终输出多组候选答案与对应的推理链。

**与自纠错闭环的联动**

- 接收反思阶段回退的「推理修正指令」：当验证发现逻辑谬误、推理跳步、路径偏差但证据本身充足时，反思阶段会输出修正方向（如 “补充第二步的推导依据”“排除与证据冲突的推理分支”）；
- 本阶段根据指令调整推理路径、补充逻辑环节、更换推导思路，重新生成推理链与候选答案，再送入验证阶段，无需回退到检索环节。

**输出产物**：多组推理链、对应候选答案、每条路径的初步置信度。



###### Q22：阶段四：事实验证（Verification）—— 闭环的检测入口

这是自纠错闭环的**核心检测层**，只负责 “发现问题、定位错误”，不做修正决策，是连接主流程与闭环的关键节点。

**主链路核心动作**

对推理阶段的输出做三维度全量校验，输出结构化错误报告：

1. **事实性校验（CoVe 验证链）**：将最终答案拆解为独立的事实断言，逐一与证据库中的原文做比对，标记出无依据断言、事实冲突断言、模糊表述断言，定位到具体缺失的信息点。
2. **一致性校验（Self-Consistency）**：对多条推理路径的答案与逻辑做一致性投票，统计答案分歧点、逻辑矛盾点，标记低共识的推理环节。
3. **双维度幻觉检测**：结合规则校验（如实体匹配、数值校验）与 LLM Judge，识别实体混淆、无中生有、逻辑跳步、因果倒置等具体错误类型，评估错误严重程度。

**与自纠错闭环的联动**

- 所有校验结果汇总为结构化错误报告，包含：错误类型、错误位置、严重等级、缺失 / 冲突的具体信息点，直接输入到自我反思阶段，作为纠错决策的唯一依据；
- 本阶段不干预主流程走向，只输出客观检测结果，决策完全由反思阶段完成，实现 “检测与决策分离”。

**输出产物**：结构化幻觉检测报告、事实一致性得分、推理置信度评分。



###### Q23：阶段五：自我反思（Reflection）—— 闭环的决策中枢

这是自纠错闭环的**指挥中枢**，负责根据验证报告做最终决策：是直接输出答案，还是触发回退修正，是整个闭环的核心控制单元。

Reflection Agent 接收验证报告，结合当前迭代次数，做出三类决策：

1. **置信度达标**：所有断言均有证据支撑、推理逻辑自洽、一致性达标，直接输出最终答案，全链路结束；
2. **置信度不达标且未达最大迭代次数**：根据错误类型，生成精准的修正指令，回退到对应前序阶段触发重跑；
3. **达到最大迭代次数**：强制终止闭环，基于已有信息输出带置信度标注的答案，避免无限循环。

**输出产物**：最终答案（带证据引用） / 定向修正指令 + 迭代次数记录。

###### 1. 代码与环境迁移

- **遇到什么：** 原始代码中充斥着大量的 cuda 字眼，比如 model.to('cuda')、inputs = inputs.cuda()，并且使用了 NVIDIA 生态的分布式训练工具。

- **怎么做：**

  - 我们在昇腾环境中安装了对应的 CANN 驱动包和 torch_npu 插件。

  - 在训练启动脚本（Python 代码）的最顶部加入 import torch_npu。

  - 把代码中的 device = 'cuda' 统一修改为 device = 'npu'。对于多卡分布式训练，我们将 PyTorch 原生的 nccl 通信后端修改为昇腾支持的 **hccl**（Huawei Collective Communication Library）：

    ```python
    # 原始代码
    # torch.distributed.init_process_group(backend="nccl")
    # 修改后
    torch.distributed.init_process_group(backend="hccl")
    ```

  - 通过这样简单的几步替换，让代码能够在 NPU 环境上跑起来不直接报错报错。

###### 2. 算子兼容性解决

- **遇到什么：** 代码跑起来后，在第一步的前向传播时突然崩溃，报错显示某个算子在 NPU 上不支持。排查后发现，LLaMA 架构中使用了 **RMSNorm（均方根归一化）**，而原始代码中导入的是一个针对 NVIDIA GPU 编写的自定义 CUDA Kernel（通常由 Triton 或 C++ 编写）。
- **怎么做：**
  - 由于这个特殊的 CUDA Kernel 无法直接在 NPU 上运行，我们首先采取了**临时替代方案**：用 PyTorch 原生的基础数学算子拼装了一个 Python 版的 RMSNorm（包含 mean、pow、sqrt 等基础算子）。
  - 虽然拼装版的算子运行效率较低，但它不依赖特定的 GPU 硬件，成功让模型顺利避开了报错，完成了前向和反向传播的初步打通。

###### 3. 精度对齐

- **遇到什么：** 模型虽然能跑了，但我们发现微调了几个 Step 之后，**训练 Loss 突然变成了 NaN（数值溢出）**，或者 Loss 下降的速度和在 A100 上完全对不上，出现了严重的精度偏差。
- **怎么做：**
  - 我们使用昇腾提供的**精度比对工具（Precision Debugger）**，在 A100 和 910B 上用完全相同的输入数据和权重，分别跑了一次前向传播，并 Dump 出每一层算子的输出 Tensor。
  - 通过工具的余弦相似度比对，我们发现在第 12 层的 Attention 计算中，由于使用了 bfloat16 精度，昇腾底层的某些指数计算（如 Softmax 内部）因为溢出保护机制的微小差异，导致数值产生了极大的偏差。
  - **解决手段：** 我们在代码中对该 Attention 的 Softmax 局部计算进行了“精度提升”，即在前向传播计算 Softmax 时，显式地将 Tensor 转换为 float32，计算完成后再转回 bfloat16 发送给下一层。重新训练后，Loss 曲线终于恢复正常，与 A100 的收敛趋势基本一致。

###### 4. 性能调优

- **遇到什么：** 精度对齐后，模型可以稳定训练了。但我们发现单步训练耗时极长，吞吐量（Tokens/second）大概只有 A100 的 35% 左右，这显然不符合 910B 的实际算力表现。
- **怎么做：**
  - 我们开启了 **Ascend Profiler** 抓取了一段训练的 Timeline（时间线）。
  - 通过可视化分析发现：
    1. 之前我们在步骤 2 中用 PyTorch 基础算子拼装的 RMSNorm，在底层被拆分成了十几个小算子频繁下发，产生了大量的 **AICPU 算子调用和 Host-Device 之间的内存拷贝**，成为了严重的性能瓶颈。
    2. Attention 计算没有利用硬件的高带宽优势。
  - **解决手段：**

  - 经过这两项优化，算子下发频率大幅降低，AICore 始终处于饱满的工作状态。最终，模型的训练吞吐量提升了数倍，达到了预期的性能指标。

###### Q2：昇腾如何分析性能瓶颈？

```markdown
# 昇腾用 MindStudio Profiler / Ascend Insights。分析算子 Execution Time（计算受限/Memory Bound）与 Communication Time（AllReduce 阻塞）。
msprof 采集的数据最终会呈现为 Timeline 轴线图（msprof.json） 和 算子明细表（op_summary.csv）。
在实际排查中，我最常看两类指标：
	在 Timeline 上看 Host 与 Device 之间的 Gap，用来定位 Python 侧下发慢或同步阻塞（Host-Bound）；
	在 CSV 表格里看 Cube 利用率与 HBM 读写带宽，用来区分算子是计算受限（Compute-Bound）还是访存受限（Memory-Bound）。

瓶颈 1：Host-Bound（Host 侧下发瓶颈 / NPU 频繁空转）
	在 Timeline 上的表现：Top 轨（Host 侧）忙得不可开交，而 Bottom 轨（NPU Device 侧）的 Kernel 之间存在大量的空白间隙（NPU Idle）。
	原因：
		Host 侧 Python 代码存在慢操作（如 CPU 上的复杂数据处理、频繁 print/日志记录）。
		代码中滥用了 torch.cuda.synchronize() 或同步拷贝，强行让 NPU 停下来等 CPU。
		小算子太密集，Host 侧下发的速度赶不上 NPU 计算的速度。

瓶颈 2：小算子下发开销大（Launch Overhead）
	在 Timeline 上的表现：NPU 轴线上全是密密麻麻如“针尖”般的小 Kernel（执行时间仅 12us），但算子与算子之间的切换间隙却长达 510us（调度开销比执行时间还长）。
	原因与解法：模型未做算子融合。需要开启 CANN 图模式、使用 MindIE/ATB 融合算子，或者用 Ascend C 重新编写融合内核。

瓶颈 3：Memory-Bound（访存密集型算子瓶颈）
	在 op_summary.csv 上的表现：LayerNorm、Softmax、RMSNorm、GeLU 等算子单次耗时很高；Vector Pipe Utilization 很高，且 Read/Write Bandwidth 接近 HBM 理论带宽峰值（如 910B 接近 1.6 TB/s），但 Cube Utilization 为 0。
	原因与解法：AI Core 的计算单元在等待数据从 HBM 显存加载到 L1/L2 Cache。需要将“访存-计算-访存”的多步操作融合成一个 Kernel，减少对 HBM 的往返读写。

瓶颈 4：Cube 利用率低 / 算子未对齐硬件（Compute Underutilization）
	在 op_summary.csv 上的表现：MatMul（矩阵乘）算子占用了大幅时间，但 Cube Pipe Utilization 只有 20%~30%。
	原因：
		Shape 未对齐：输入的 Batch Size 或 Hidden Size 没有按昇腾推荐的 16 / 32 / 128 字节/元素对齐，导致 AI Core 内部无法满矩阵填充计算。
		动态 Shape 频繁触发重编译：频繁地动态改变 Sequence Length。

瓶颈 5：通信未掩盖（Communication Non-Overlap）
	在 Timeline 上的表现：在多卡（TP/PP）场景下，通信 Kernel（如 HcomAllReduce）单独占据了一整块时间轴，前后完全没有 AI Core 的 Compute Kernel 在并行执行。
	原因与解法：没有实现计算与通信的重叠（Overlap）。需要检查流水线并行（PP）的 1F1B 策略或张量并行（TP）的 Ring-AllReduce 是否正确配置了异步通信流（Stream）。
```



###### Q3：你们在昇腾 910B 上做推理部署，遇到最难的性能/兼容性坑是什么？怎么解决的？

###### Q4：如何昇腾上适配新的LLM模型？

```python
# 这套适配流程可以总结为 5 个标准阶段：算子评估 -> 模型组图 -> 权重映射 -> 精度对齐 -> 性能调优。
# 第一步：可行性打通与算子替换（跑通 Eager 模式）
目标：不考虑性能，先让模型在 NPU 上使用 PyTorch（torch_npu）跑通一次 Forward/推理。
1.算子兼容性排查（核心攻坚）：
    优先替换为 torch_npu 官方高性能算子：例如将自定义的 FA2 替换为 torch_npu.npu_flash_attention；将 RMSNorm 替换为 torch_npu.npu_rms_norm；将 RoPE 替换为 torch_npu.npu_rotary_mul。
    降级为 PyTorch 原生算子 (ATen)：若无对应硬件加速算子，先用纯 PyTorch 算子重写逻辑（如用基础的 torch.matmul + softmax 替代 Attention），确保逻辑正确。

# 第二步：精度对齐（逐层输出比对）
目标：确保 NPU 上跑出来的 Token 输出和 GPU（或 HuggingFace 原生）完全一致，防止出现“能跑但输出乱码”的情况。
1.环境对齐：
	固定随机种子（torch.manual_seed）。
	推荐统一使用 BF16 数据类型（昇腾 910B 对 BF16 原生支持极佳，FP16 在深层 Transformer 中易发生梯度/数值溢出）。
2.逐层 Hook 抓取 Tensor 与余弦相似度（Cosine Similarity）比对：
	编写 Hook 脚本，分别在 GPU（基准）和 NPU 上输入完全相同的 Prompt。
	依次抓取并比对以下节点的 Output Tensor：
		Embedding 层输出
		Transformer Layer 1（Self-Attention 前/后、MLP 前/后）
		Final LayerNorm 输出
		LM_Head 的 Logits
	判定标准：每一层的 Cosine Similarity 应大于 0.999。若某一层相似度突降（如从 0.99 掉到 0.85），则锁定了产生精度漂移的“问题算子”。
    
# 第三步：高性能推理引擎集成（入库 vLLM-Ascend 或 MindIE）
1.路线 A：集成到 vllm-ascend（社区/通用路线）
    注册新模型架构：在 vllm/model_executor/models/ 下新建模型文件。
    替换为 vLLM 逻辑层：
    	将 nn.Linear 替换为 vLLM 的 ColumnParallelLinear / RowParallelLinear（实现多卡张量并行 TP）。
    	将 Attention 替换为 vLLM 的 Attention 模块，其底层会自动调用昇腾适配的 PagedAttention NPU Kernel。
    适配 Weight Loader：编写权重加载逻辑，映射 HuggingFace 的权重 Key 名。
2.路线 B：集成到 MindIE / ATB Models（华为官方最高性能路线）
    如果寻求极致吞吐，需接入昇腾 ATB (Ascend Tensor Boost) 加速库：
    定义 ATB 图结构：使用 C++ 或 ATB Python API 组装模型的计算图（定义 Tensor Node 和 Operation Node）。
    调用融合 Operation：直接调用 ATB 预置的 LinearParallelOperation、PagedAttentionOperation、RmsNormOperation。
    MindIE Service 打通：将 ATB 模型打包为 .so 动态库，配置 config.json，由 MindIE Service 统一加载进行 Continuous Batching 管理。

第四步：性能 Profiling 与瓶颈调优（跑快）
模型能上线后，使用 msprof / MindStudio Profiler 进行最终的性能打磨。
1.消除动态 Shape 导致的重编译（JIT Overhead）：
	问题：NPU 图模式对动态 SeqLen 非常敏感，每次长度变化都可能触发 CANN 重新编译图。
	优化：开启 Bucket（分桶）机制（如 256, 512, 1024），将输入 Padding 到固定的 Bucket 长度，或者使用 Chunked Prefill 固化计算 Shape。
2.提升 AI Core 算子利用率：
	查看 op_summary.csv，确保 MatMul 和 Attention 的 Cube Pipe Utilization 在 60% 以上。
3.多卡通信重叠（HCCS Overlap）：
	在多卡张量并行（TP）下，利用 Profiler 查看 HcomAllReduce 通信算子是否与前后的 MatMul 计算重叠，调整通信 Stream 优先级。

```



###### Q5：既然有了 vLLM，为什么推理平台还要引入 SGLang？

```python
1. 场景分化：vLLM 是极佳的“通用吞吐型引擎”，但在 Agent 和 RAG 场景有局限。
```

###### Q5：ZeRO 的几种阶段

在传统的数据并行（Data Parallelism, DP）中，每个 GPU 都会完整地复制一份模型参数（Parameters）、梯度（Gradients）和优化器状态（Optimizer States，例如 Adam 优化器中的动量和方差）。这会导致极大的显存冗余。

ZeRO 通过**分片（Partitioning）**的方式消除了这种冗余。它分为以下几个阶段：

| 阶段 (Stage) | 分片内容                                                 | 显存减少量 (估算)             | 特点与适用场景                                               |
| ------------ | -------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| **ZeRO-1**   | 仅对**优化器状态**（Optimizer States）进行分片           | 约减少到原来的 1/4            | 每个 GPU 只保存和更新一部分优化器状态。通信开销较小，适合显存略微不足的场景。 |
| **ZeRO-2**   | 对**优化器状态 + 梯度**（Gradients）进行分片             | 约减少到原来的 1/8            | 每个 GPU 在反向传播后，只保留它所负责更新的参数对应的梯度，其余梯度释放。性能和显存节省的平衡点。 |
| **ZeRO-3**   | 对**优化器状态 + 梯度 + 模型参数**（Parameters）进行分片 | 显存占用与 GPU 数量呈线性反比 | 彻底消除冗余。在前向和反向传播时，GPU 动态从其他节点拉取所需的参数，计算完毕后立即释放。通信开销最大，但能训练超大规模模型。 |

**补充：ZeRO-Offload 与 ZeRO-Infinity（异构显存技术）**

为了在单卡或少量显卡上训练更大的模型，DeepSpeed 引入了 Offload 技术，将显存压力分摊到主机内存（CPU RAM）或硬盘（NVMe SSD）上：

- **ZeRO-Offload**：将**优化器状态**和**梯度**从 GPU 显存卸载（Offload）到 CPU 内存上进行计算和存储。
- **ZeRO-Infinity**：在 ZeRO-3 的基础上，利用 NVMe 固态硬盘、CPU 内存和 GPU 显存构建三级存储，支持将**模型参数**也卸载到 NVMe/CPU。这使得在单张 GPU 上运行万亿参数模型的微调或推理成为可能，但代价是训练速度会受限于数据传输带宽。

###### Q15：你说收益递减，依据是什么？

```markdown
参考Scaling Law。
模型能力近似满足：
L(N)=AN−α+B

其中：
N = 参数量
L = Loss（Loss 越小，模型能力、精度、效果越好）

随着参数增加：
Loss下降越来越慢

	我们判断收益递减，主要依据大模型缩放定律。模型损失 Loss 和参数量满足幂函数关系，参数量越大，Loss 下降速度越慢。结合通信场景实测：7B 到 14B、14B 到 32B 参数扩容收益都很可观，但从 32B 提升到 72B 后，效果提升明显放缓，因此判定已经进入边际收益递减区间。
```

###### Q36：长上下文能力是通过继续预训练自然获得的，还是单独做了 long-context adaptation（比如 RoPE scaling / NTK / YaRN）？

```markdown
工业界基本是“混合方案”，不是二选一
可以理解为三段式：
    模型结构层（必须）：扩展 position encoding 上限
    训练层（关键）：注入长依赖分布
    对齐层（最后）：让模型学会“正确用长上下文”

长上下文能力一般不是单靠 continued pretraining 自然获得的，而是一个“结构改造 + 数据课程学习 + 对齐训练”的组合过程。

如果只做 continued pretrain，在 RoPE 或位置编码没有处理的情况下，模型会在 extrapolation 阶段出现 attention distortion，远距离 token 的有效性会显著下降。
```

###### Q41：为什么要做 CPT（持续预训练）？RAG 不够用吗？

1. **Tokenization 碎裂问题**：通用大模型对通信领域专有名词（如 gNodeB、Option 3x、QCI_9、RRCReconfiguration）切词极碎。CPT 能够优化模型对通信专用 Token 的表征效率，**节省 Context 窗口，提升 Attention 集中度**。
2. **隐式逻辑推理（Parametric Reasoning）**：RAG 只能提供“上下文片段”，但**故障诊断和告警拓扑分析**需要模型理解通信协议栈的隐式因果链（如：PHY层 CRC 错误 -> MAC 层 HARQ 重传 -> RLC 状态报告 -> RRC 断连）。CPT 调整的是模型底层的概率分布和推理拓扑，让它“天然具备通信领域的直觉”。
3. **最终架构权衡**：我们采用了 **“CPT/SFT 建立基座能力 + RAG 提供实时/确定性数据”** 的双轮驱动模式，而不是非此即彼。



###### Q42：如何解决合成数据的“自举悖论”与“幻觉循环”？

1. **拒绝无约束自由生成**：不让 LLM“凭空造题”，而是**以真实的通信日志、设备 CLI 指令集、3GPP 标准 AST（语法树）为硬性约束（Anchor）**。LLM 只负责包装 Prompt 和改写表达，逻辑骨架来自真实系统。
2. **确定性代码/规则校验器（Deterministic Validators）**：
   - 对于故障诊断场景：写正则和 Python 脚本，自动校验生成数据中的 CLI 命令语法是否合法、参数范围是否超限。
   - 对于标书分析场景：校验提取的表格字段与源文件 JSON Schema 是否完全匹配。
3. **验证成本 < 生成成本**：利用大模型“生成难、验证易”的特性，采用“小模型生成候选 -> 规则过滤 -> 强模型/通信专家盲审”的漏斗机制。



###### Q43：DPO 对齐陷阱：垂直领域的“偏好”到底是什么？如何避免 Reward Hacking？

1. **惩罚“冗长与废话”**：在故障诊断场景，运维人员需要极高效率。我们将**步骤过长、包含无意义客套话、或者推理链条过长但没有给出明确 CLI 排查命令**的回答，直接标为 yrejected。
2. **高危动作负偏好**：通信场景最忌讳“误操作导致基站大面积断网”。如果 Rejected 样本中包含高危指令（如未带过滤条件的高负载查询指令或高危重启指令），其惩罚权重拉满。
3. **控制 DPO 长度偏置**：采用 **Length-Normalized DPO** 或在构建 (ychosen,yrejected)对时，**严格控制两者的长度差（Length Matching）**，消除模型通过“翻倍输出长度”来骗取 Reward 的行为。



###### Q44：QLoRA 在 CPT 和 DPO 上的表达上限折损

1. **承认局限性**：实验表明，在 **CPT（增量预训练）阶段**，QLoRA 由于基座 4-bit 冻结，吸收新知识（Knowledge Capacity）的上限确实明显弱于 Full-FT。

2. **分阶段工程拆解（关键思考）**：

   - **CPT 阶段**：放弃 QLoRA，采用 **DeepSpeed ZeRO-3 + Offload** 进行 **Full-FT 或高 Rank（如** r=256）的 LoRA**

     ，保证模型对通信领域新知识的“消化能力”。

   - **SFT / DPO 阶段**：此时模型已经具备领域知识，主要是学习指令格式与行为对齐，参数改动量小，此时全面切入 **QLoRA (**r=64, 全 Linear 层挂载)，将训练成本降低 70% 以上。

3. **精度损失补偿**：在 QLoRA 中使用 bf16 混合精度，且必须作用于所有 Linear 层（Q, K, V, O, Gate, Up, Down），否则领域能力的泛化会显著受损。



###### Q45：15% 的准确率提升和 7% 的幻觉下降是怎么防刷榜（Overfitting）的？

1. **防数据泄露（OOD 动态评测集）**：评测集**严禁**使用已有的规范文档。我们使用**最近 1 个月内发生的真实脱敏运维故障工单**和**最新的通信设备升级日志**作为测试集（此时模型训练数据尚未覆盖）。
2. **幻觉率的定量定义**：
   - 构建**通信实体/参数规则库**。如果模型生成的答案中，包含了不存在的参数名、错误的命令语法、或与提供上下文矛盾的推论，计入 1 次幻觉。
   - 幻觉率下降 7% 指的是：在 1000 条复杂故障诊断 Prompt 下，经规则库自动校验 + 专家抽样核验，产生“严重幻觉（高危错误）”的样本比例由 12% 降至 5%。
3. **线上数据闭环（真正的落地）**：
   - 在智能运维 Portal 中埋点，提供“采纳”、“修改后采纳”、“拒绝”三个按钮。
   - 工程师**“修改后采纳”的对比数据**（工程师改动前的模型输出 vs 工程师修改后的最终输出），被自动洗成最高质量的 DPO 偏好对（Rejected vs Chosen），反哺下一代模型训练。

###### 46：扩充词表到底是“救命药”还是“毒药”？

1. **决策权衡（To Expand or Not）**：
   - 扩充词表可以提升 20%~30% 的文本压缩率（提升推理吞吐，降低上下文长度），但代价是**打破了原模型精心训练的 Embedding 空间**，需要大量的 CPT 语料（至少百 GB 级）才能重新将新 Token 训练收敛，否则新 Token 会导致模型产生严重语法混乱。
2. **工程解决方案**：
   - **如果不扩词表**：在 CPT 阶段，针对通信专有名词进行 **Subword 拼接训练**，利用 Sample Packing 缓解 Padding 浪费，靠算力硬抗。
   - **如果扩词表**：只扩充高频通信词（如 3000~5000 个），新 Token 的 Embedding 采用 **原词表中对应 Subword 的 Embedding 平均值（Mean Initialization）** 进行初始化，并在 CPT 早期**冻结除 Embedding 和 Head 以外的参数**（Warmup 阶段），先单训新词表，再做全量/LoRA 增量训练。



###### 47：智能运维与招投标分析抢占参数空间怎么办？

1. **梯度冲突现象**：招投标任务鼓励模型输出“详尽、多角度的自然语言”，而运维诊断要求“极简、高精准度的逻辑/指令”。直接混合训练会导致 Loss 震荡，诊断准确率下降。
2. **解题手段一：任务概率采样与分阶段 SFT**：
   - 采用 **Temperature-based Dynamic Sampling** 调节不同任务的采样权重。
   - 先用大比例的“通用问答+招投标长文本”训练语言基础能力，再用高质量的“故障诊断结构化数据”进行收尾微调（Annealing 阶段）。
3. **解题手段二：Multi-LoRA / MoE 架构解耦（高阶架构选型）**：
   - 线上部署时，底座模型统一，但针对“招投标”和“智能运维”挂载不同的 **LoRA Adapter**，在前置系统（Router）根据 User Intent 动态路由加载对应的 Adapter，从物理上隔绝参数干扰。



###### 48：超长上下文与长依赖陷阱：招投标分析中的“Lost in the Middle”

1. **长文本 SFT 训练技巧**：
   - 纯粹靠外推（如 YaRN / RoPE Scaling）扩展上下文会导致模型在中间段落的注意力弥散（Lost in the Middle）。
   - 在长文本 SFT 数据构建时，**故意将“关键决策信息（Needle）”放置在文本的中段（10%~90% 随机位置）**，强迫模型在 SFT 过程中学会全局 Attention 扫描。
2. **工程降本（Chunk-based Hierarchical Processing）**：
   - 放弃将整个标书一次性塞入 Prompt 的“莽夫方案”。
   - 采用 **“分块提取（Map） -> 结构化摘要 -> 全局对比决策（Reduce）”** 的 Chain-of-Thought SFT 范式，将 50K 的长文本任务拆解为小窗口并发处理，大幅提升长文档指标提取的无遗漏率。



###### 49：生产环境部署的“最后一公里”：PTQ 量化导致的通信指令精度崩塌

“你们训练用 QLoRA，最后部署时肯定要合并权重（Merge Adapter）并用 vLLM / TensorRT-LLM 部署。**为了追求高并发，通常会对 Merge 后的模型做 AWQ / GPTQ 4-bit/8-bit 量化。但量化往往会导致精确语法（如网管 CLI 命令）出现字符错乱**，你们遇到了吗？如何解决生产部署的精度崩溃？”

1. **混合精度量化（Selective Quantization）**：
   - AWQ/GPTQ 全量化会导致某些对字符极其敏感的层（如 LM Head 和部分关键 Transformer 层）精度受损。
   - 通过计算激活值敏感度（Activation Sensitivity），**将 LM Head 和关键层保留为 FP16 / FP8，仅对其余层做 INT4/INT8 量化**。
2. **解码端硬约束（Grammar-Guided Decoding / GBNF）**：
   - 模型推理层面，在 vLLM 后端挂载 **Outlines 或 GBNF (GGML Backus-Naur Form) 语法树**。
   - 当模型生成网管 CLI 命令或 JSON 诊断结果时，强制在 Logits 采样阶段 Mask 掉不符合通信语法规范的 Token，保证 100% 输出合法命令，将“量化导致的语法错误”在推理解码阶段直接拦截。



###### 50：通信领域“小语料”CPT 的“数据饱和”与“过拟合/幻觉爆炸”博弈

1. **数据重复（Epoch > 2）的毒性**：领域小语料如果重复训练超过 2 个 Epoch，模型会迅速将文本“死记硬背”，表现为 Loss 极低，但遇到微小的参数扰动（如更改网络拓扑中的 IP 地址）就会死板输出固定的错误日志片段。
2. **训练策略**：
   - **严格限制 Epoch** ≤1.5：绝不为了降 Loss 而在小语料上过度循环。
   - **动态学习率与数据交织**：采用带有衰减控制的 Learning Rate（如从 5e−5 线性衰减至 5e−6），并在 CPT 中交织 **15% 的通用高质量代码与逻辑推理语料**（如 OpenHermes、Code Llama 采样）。
3. **Stop Signal（停止信号）**：设置 Validation Set 监控两类指标——当通信领域验证集 PPL 降幅小于 1% **且** 通用逻辑推理 benchmark（如 MMLU/GSM8K 子集）准确率下降超过 2% 时，立即触发 Early Stopping。

###### 51：增量对齐与数据飞轮中的“流式更新灾难”（Incremental SFT/DPO Collapse）

1. **经验回放缓冲池（Replay Buffer）机制**：
   - 建立一个固定规模（如 10,000 条）的 **Anchor 数据集**，包含历史训练集中最具代表性的各子任务数据（故障诊断、标书提取、规范问答）及基座通用能力数据。
   - **数据混合微调**：当新增 500 条 Badcase 数据时，并不单训这 500 条，而是从 Replay Buffer 中按 1:4 的比例抽样历史老数据（2000 条），组成 2500 条的增量 Batch 进行微调。
2. **LoRA 级别的物理隔离**：
   - 如果新增数据属于全新的子业务（例如新增了“5G RedCap 专项网管”），则**不修改原有 LoRA 参数**，而是训练一个新的子 Adapter，利用 Router 在推理时进行动态加载，避免污染主模型。

###### 52：显存与硬件瓶颈问题：显存溢出（OOM - Out of Memory）

- **现象**：训练刚开始或跑了几步后突然报 CUDA out of memory。

- **解决办法**：

  - **参数高效微调（PEFT/LoRA）**：改用 **LoRA / QLoRA**（4-bit 量化微调），可将显存需求降低 60%~80%。

  - **梯度累积（Gradient Accumulation）**：减小单卡 Batch Size（如设为 1 或 2），通过梯度累积达到目标 Total Batch Size。

  - **梯度检查点（Gradient Checkpointing）**：以计算时间换显存，大幅降低激活值（Activation）占用的显存。

  - **混合精度训练**：使用 bf16（首选，硬件支持 Ampere 及以上架构）或 fp16。

  - **分布式显存优化**：使用 **DeepSpeed (ZeRO-2 / ZeRO-3)** 或 PyTorch **FSDP**，将模型状态分片到多张 GPU 上。

  - **上下文长度裁剪**：适当缩短最大序列长度（max_length），因为 self-attention 的显存开销随长度呈二次方O(N2)增长。可配合 **FlashAttention-2/3** 降低显存开销。

    

###### 2. 训练速度极慢

- **现象**：GPU 利用率（GPU-Util）低、数据加载瓶颈，或每秒处理 Token 数太少。
- **解决办法**：
  - 开启 **FlashAttention-2** 或 SDPA（Scaled Dot-Product Attention）。
  - 优化 DataLoader：增加 num_workers，开启 pin_memory=True。
  - 使用高效微调框架：如 **Unsloth**（可提升 2-5 倍训练速度并节省显存）、**LLaMA-Factory**、**Deepspeed**。

###### 二、 训练过程与 Loss 异常问题

Loss 变为 NaN 或 Inf（梯度爆炸/数值溢出）

- **现象**：训练几百步后 Loss 突然变成 NaN，训练崩溃。
- **原因**：FP16 动态范围较小容易上溢，或学习率过大、数据中存在异常值。
- **解决办法**：
  - **改用 bf16**：BF16 的数值范围与 FP32 一致，极少发生溢出。
  - **梯度裁剪（Gradient Clipping）**：设置 max_grad_norm = 1.0 或更小（如 0.5）。
  - **调小学习率（Learning Rate）**：LLM 微调的学习率通常非常小（全量微调：1e−5∼5e−6；LoRA：1e−4∼3e−4）。
  - **清洗数据**：排查数据集中是否存在极长文本、空文本或非法字符。

###### Loss 不下降 / 无法收敛

- **现象**：训练多个 Epoch 后，Loss 居高不下或平躺。

- **解决办法**：

  - **排查 Prompt 模板**：检查训练数据格式是否与基座模型的 Chat Template 一致（如 <|im_start|> 等特殊 Token 是否正确插入）。

  - **增加 Warmup 步数**：加入 3%~5% 的 Learning Rate Warmup。

  - **检查 Loss Masking**：确保计算 Loss 时**只对 Model Response 计算，Mask 掉 User Instruction**（即 train_on_inputs=False）。如果对 Prompt 也计算 Loss，模型容易学偏。

  - **增加 LoRA 的 Rank (**r) 和 Alpha**：如果用了 LoRA，可能是可训练参数太少，可以尝试将 r 从 8 提高到 64 或 128。

    

###### Loss 突然飙升（Loss Spike）

- **现象**：Loss 本来很平滑，突然产生一个巨大的尖峰，然后又慢慢下降或直接崩掉。

- **解决办法**：

  - 调低学习率，增加 Warmup。

  - 增大 Batch Size（或增加梯度累积步数），使梯度估计更稳定。

  - 调整 AdamW 优化器参数：例如将 β2 从 0.999 改为 0.95 或 0.98。

###### 三、 模型效果与泛化能力问题

###### 灾难性遗忘（Catastrophic Forgetting）

- **现象**：微调后，模型在特定领域变强了，但失去了通用对话、逻辑推理或代码能力，甚至连基本的问答格式都乱了。
- **解决办法**：
  - **数据混采（Data Replay / Mixing）**：在领域数据中混入 5%~10% 的通用高质量数据（如 ShareGPT、Alpaca 或 SlimPajama）。
  - **优先选择 LoRA 微调**：LoRA 保留了冻结的基座权重，相较于全量微调更容易保留基座模型的通用能力。
  - **使用权重衰减（Weight Decay）和较低的 Epoch 轮数**：微调数据量不大时，通常 1~3 个 Epoch 足矣，避免多轮训练。

###### 模型过拟合（Overfitting）与死记

- **现象**：训练集的 Loss 降得非常低，但测试时稍微改变问法，模型就无法正确回答，甚至直接复读训练集原句。
- **解决办法**：
  - **提高数据多样性**：扩充同一指令的不同表达方式（Prompt 多样化）。
  - **减少训练 Epoch**：很多情况下，微调数据集跑 **1~2 个 Epoch** 效果最好。
  - **早停法（Early Stopping）**：监控 Validation Loss，一旦验证集 Loss 开始上升立即停止。

###### 复读机现象 / 幻觉严重 / 乱码输出

- **现象**：模型不断重复上一句话，或者输出不符合逻辑的胡言乱语。
- **解决办法**：
  - **检查 EOS Token（结束符）**：确保训练数据结尾正确添加了模型对应的 <|im_end|> 或 </s>，否则模型不知道何时停止，容易狂吐重复字符。
  - **推理采样参数调整**：微调后需要重新调整推理参数（Temperature 降至 0.1~0.7，开启 Repetition Penalty，设置 top_p 等）。
  - **清洗低质数据**：检查训练集中是否有大量的长文本重复或质量极差的 LLM 生成数据。

------



###### 四、 数据与格式问题（“垃圾进，垃圾出”）

###### Special Tokens 错误处理

- **现象**：模型把控制标记（如 <|im_start|>）当成普通文本打印出来，或者无法识别对话轮次。
- **解决办法**：
  - 使用官方提供的 Tokenizer 和 apply_chat_template 方法。
  - 确保自定义的新 Token（如有）已被成功添加至 Tokenizer 且词表已被扩展（Resize Token Embeddings）。

###### 数据质量差、噪声多

- **现象**：微调后模型回答生硬、含有错误事实或模仿了数据里的低级错误。
- **解决办法**：
  - **高质量胜过大数量**（Quality > Quantity）：1,000 条高质量、经人工精细校对的 SFT 数据，效果远好于 10 万条爬虫抓取的噪声数据。
  - **去除重复数据**：对 SFT 数据进行 Deduplication（去重）。

```markdown
5. LLM作为裁判的语义裁决
```

##### Q4：为什么不用 RAG？

```markdown
# 不让使用embedding，无法获取语义相似度
```

##### Q5：你们怎么做“检索 few-shot 示例”的？完全不用向量模型吗？

```markdown
Rule-based + Label-aware Selection

具体做法：
    基于标签分桶（label bucket）
    基于历史误分类样本池（error memory）
    基于规则匹配（关键词 + 模板匹配）
   	Boundary-first sampling（优先选“模型曾经错过的样本”。）
```

##### Q6：没有 embedding，你怎么判断“边界样本”？不会很主观吗？

```markdown
我们不是语义相似度判断，而是用行为信号定义边界样本。
边界样本定义为：

模型历史上：
    1. 预测错误
    2. 或置信度低（logprob proxy）
    3. 或多次预测不稳定
```

##### Q7：你说你做了 Context Pipeline，这一套到底解决了什么问题？为什么普通 Prompt 不行？

```markdown
普通 Prompt 在长上下文中有两个核心问题：
1️⃣ 信息衰减
    early token 被弱化
    instruction 被覆盖
2️⃣ 结构混乱
	few-shot 示例和规则混在一起，模型无法区分优先级

我们 Context Pipeline 做了结构化：
    System
    ↓
    Task Card
    ↓
    Boundary Definition
    ↓
    Few-shot
    ↓
    Constraint
    ↓
    Query
让模型“按层理解任务”，而不是混读
```

##### Q8：为什么 Task Definition Card 能提升效果？它本质不还是 prompt 吗？

```markdown
👉 降低认知负担（Cognitive Compression）

我们做了三件事：
    把任务拆成固定 schema
    每个 schema 是短句 + 强约束
    避免自由描述
```

##### Q9：Token Budget Optimization，具体怎么控制 k∈[3,20]？

```markdown
我们不是固定 k，而是动态计算：
	k = min(max_score_samples + boundary_samples, budget / avg_token_length)

策略：
    budget = 模型最大 context - system - query
    boundary samples 优先占位
    剩余填高置信样本
```

##### Q10：你说你做了 Multi-Class GRPO，它和普通 GRPO 本质区别是什么？

```markdown
普通 GRPO 是在单样本维度做 group relative optimization：
    同一个 prompt
    多个 sampling trajectory
    做 reward 相对比较

👉 本质是：sample-level ranking learning
而我们提出的 Multi-Class GRPO 是：
👉 batch-level + multi-class constraint 的 GRPO 变体

核心变化有三点：
1️⃣ batch 内包含多个类别（不是单任务 group）
Batch = {class1, class2, class3 ...}

而不是：
Batch = same prompt multiple outputs
2️⃣ 引入跨类别边界竞争机制
我们不只是比较“同类输出好坏”，而是：
👉 跨类别之间也参与 reward competition

例如：
“投诉 vs 咨询”
“故障定位 vs 故障处理”
模型必须在 batch 内做结构性区分。

3️⃣ reward 控制“可更新经验数量”
我们设计了一个关键机制：
    reward ↑  → 可更新经验 ↓
    reward ↓  → 可更新经验 ↑

直觉是：
    高 reward：说明当前 batch 已经稳定 → 不需要大幅更新
    低 reward：说明边界不清 → 加大经验更新力度
```

##### Q11：你这个“reward 控制更新经验数量”具体是什么意思？听起来不像标准 RL

```markdown
确实不是标准 RL 设计，我们做的是：

👉 把 GRPO 从“优化目标函数”改成“控制学习节奏的机制”
具体实现是：
Step1：计算 batch reward score
	R_batch = mean(correct samples) - mean(error samples)
Step2：映射 update quota
	update_ratio = sigmoid(α - R_batch)
Step3：控制 replay buffer 更新量
	reward 高 → 只更新少量 hard samples
	reward 低 → 扩大 error samples 回灌

👉 本质是：
reward 不只是“优化信号”，还是“经验流动控制器”
```

##### Q12：你说 batch 内跨类别比较，但不同类别本身语义不同，怎么保证可比性？

```markdown
👉 比较“分类决策一致性”而不是语义相似性
跨类别比较的不是“内容”，而是：
👉 分类边界清晰度

例如：
    咨询 vs 投诉
    是一个 decision boundary problem
    
👉 Multi-Class GRPO 本质不是跨语义比较
👉 而是跨 decision boundary 的结构优化
```

##### Q13：你说 batch reward 控制经验更新，那如果 batch 全对或者全错怎么办？

```markdown
GRPO 只在“部分正确但存在边界模糊”时才有效
```

##### Q14：你这个机制听起来像“训练控制策略”，那它和 curriculum learning 有什么区别？

```markdown
确实有相似性，但有本质区别：
Curriculum Learning：
    预定义难度顺序
    静态 schedule

Multi-Class GRPO：
👉 动态结构学习
区别在三点：
1️⃣ difficulty 不是预设的
而是：
difficulty = model error + boundary instability

2️⃣ batch 内是竞争结构
不是“简单排序”，而是：
👉 class-level competition

3️⃣ reward 控制的是“经验流动”
不是 sample selection，而是：
experience update rate
```

##### Q15：那你这个方法稳定吗？会不会出现训练震荡？

```markdown
❌ 问题1：reward oscillation
batch reward 在：
高正确率 ↔ 突然崩溃
解决：
	EMA smoothing reward：
	由于 batch 内跨类别竞争，reward 波动比较大，所以我们引入 EMA 对 reward 进行平滑，减少单 batch 偶然性对训练的影响。
	clip update ratio：
	为了避免 reward 过低时导致策略更新过激，我们对 update ratio 做了 clip，限制每次 policy 更新的最大幅度。

❌ 问题2：class dominance
某些类别长期高 reward
解决：
	class-balanced replay buffer：
	由于不同类别难度不同，容易出现 class dominance，我们用 replay buffer 做类别均衡采样，防止模型偏向高频或容易类别。
```
